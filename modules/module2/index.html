Module 2: Spec Creation¶

Continue in the same session as Module 1 and bring your requirements.md in as context. The exploration you just did is what lets the agent plan against real files and line numbers, rather than in the abstract.

The agent's autonomy goes up here. You'll draft in Plan mode, but the plan is yours. Requirements are the input; the spec is the output: the one document Module 3 will build from. Your job is to iterate with the agent until that document is right, before a line of code is written.

1. Frame the Requirements¶

Before you ask for a plan, pin down the inputs yourself, grounded in your requirements.md:

  • What the system should do (functional)
  • The constraints it must hold (security, performance, scale)
  • The edge cases and failure modes
  • What's explicitly out of scope

2. Generate an Initial Plan¶

Hand the agent your requirements and ask it to draft a development plan broken into phases. Treat this first draft as raw material: your starting point, not your spec.

"Using my requirements and notes, draft a phased implementation plan for [your request]. Don't write code yet."

3. Own the Plan: Review and Cut¶

Read every phase. Decide yourself what's necessary, what's bloat, and what doesn't belong. This is where ownership is won or lost: rubber-stamp the first draft and you've handed the agent your design. Cut, reorder, correct.

Check it both ways: is anything missing (a requirement or validation criterion from Module 1 with no step behind it), and is anything too vague? Reject non-steps like "implement X"; each phase should be concrete enough to act on and to test.

4. Refine Until it Holds Together¶

Iterate before you implement, by hand or with the agent's help:

  • Refine as you review: keep reading and correcting the spec yourself
  • Interview mode: have the agent question you about the spec, one decision at a time
  • Refine through execution: let it attempt a slice, then fix the spec with what you learn

"Interview me about this spec, one question at a time, on anything ambiguous or unspecified."

Tip

Stop at a minimum viable spec: one where you understand and accept the architectural decisions and their level of detail. Don't over-invest chasing perfect.

5. Build in Validation and Checkpoints¶

For each phase, define how you'll know it's done (ideally something the agent can run on its own, like a test). Then mark the points where you need to pause for human judgment on things a test can't catch.

6. Write it to spec.md¶

That document is the output of this module and the core input to Module 3. If it's clear enough that someone else could implement from it, you're ready.

Tip

Keeping yourself in the loop through an interactive back-and-forth (where the agent questions you about your own spec) is the fastest way to catch gaps without quietly handing design decisions to the agent.
