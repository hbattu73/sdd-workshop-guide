Module 3: Verification¶

Setup: Work from the change you built in Module 2. This is where ownership and trust climb back up: the agent generated the code, now you take responsibility for it. The agent helps you review; the judgment is yours.

1. See the Blast Radius¶

git diff --stat main

One screen: every file the implementation touched and how much. Read it before anything else.

2. Review it Yourself First¶

Open one file and read it as the author, not a spectator. This is how you take ownership back from the agent. Watch for the classic AI code smells:

  • Dead code, hardcoded values, and half-finished abstractions
  • Missed edge cases and outdated library usage
  • "Lazy" shortcuts: less code instead of correct code
  • Locally correct but globally wrong: right in the file, wrong for the system

Sort what you find: structural gaps go back to the spec, content errors you fix, loose code you tighten.

3. Run the Built-in Review¶

Run /review, compare against main, include uncommitted changes, and start it. Read the findings.

Don't click "Fix with Bob." A fix the agent applies to its own work is a decision you didn't make. Fixes go through the spec (step 6), not through a button.

4. Run an Independent Review¶

Start a new session in Ask mode and have it review the diff against your spec and requirements: does the code match the spec, is it safe for a regulated fintech app, and would the tests actually fail if a requirement were broken?

"Review the diff against @spec.md and @requirements.md: does the code match the spec, is it safe for a regulated fintech app, and would the tests fail if a requirement were broken? Skip what matches. Report what matters and mark which findings need a human decision."

Why a new session

The agent that wrote this code shares its own blind spots. Review it in the same window and you get the same assumptions on both ends: code that appears correct, passes its own review, and is still missing something. A fresh session reviews the diff, not the memory of writing it. Even so, notice what it doesn't raise: a diff review sees what's there, never what was never written.

5. The Human Gate¶

Three questions, answered by you, not the agent:

  1. What did /review find that the independent review didn't, and the reverse?
  2. Of the findings marked as needing a human decision, which would block shipping at your organization?
  3. Would this ship, and who signs?

Judge by blast radius (how much it can break) and use-case sensitivity (how much it matters if it does).

6. Close the Loop (optional)¶

If a finding is real, the fix belongs in the spec, not in a patch. Add the agreed change to the relevant phase of spec.md, switch to Agent mode, and re-implement that phase only.

"Phase N of @spec.md changed. Re-implement that phase and run its checks."

This is the whole discipline in one move: the spec stays the source of truth, and the code follows it.

Tip

AI fits into your existing review and governance process; it doesn't replace it. If you have a neighbor, swap diffs and review each other's change: a human reviewing AI code they didn't commission is exactly what breaks the loop. End this module with code you'd put your name on.
