Module 4: Verification¶

Setup: Work from the change you built in Module 3. Start with git diff --stat, which shows you the blast radius in one screen.

This is where ownership and trust climb back up: the agent generated the code, now you take responsibility for it. Bob is a verification tool (it helps you test and review), but the judgment is yours.

Verification has two flavors: testing and review. Neither is optional, especially the review, and especially on anything with shared ownership.

1. Set Your Verification Gates¶

Before you look at the diff, decide what "good enough to ship" means for this change: correctness, security, performance, scalability. Those gates are the bar you'll hold the code to.

2. Review it Yourself First¶

Read the diff as the author, not a spectator: this is how you take ownership back from the agent. Watch for the classic AI code smells:

  • Dead code, hardcoded values, and half-finished abstractions
  • Missed edge cases and outdated library usage
  • "Lazy" shortcuts: less code instead of correct code
  • Locally correct but globally wrong: right in the file, wrong for the system

Sort what you find: structural gaps go back to the spec, content errors you fix, loose code you tighten.

3. Check the Tests¶

Run the suite, then ask the sharper question. Not "what percentage is covered" but which of your validation criteria have no test behind them:

"Which validation criteria in my requirements have no automated test covering them?"

Coverage gaps are where the bugs you didn't catch are hiding. Closing one is a good use of the time you have left.

4. Run an AI-assisted Review¶

Have Bob summarize the changes and flag concerns as a second set of eyes. Then do the part only you can: separate real issues from noise, and the things that need human judgment from the things an agent can settle. Bob assists; it doesn't sign off.

"Review this diff against my spec. Summarize what changed and flag anything risky, incomplete, or inconsistent."

The AI Review Ouroboros

The agent wrote this code, and now the same agent is reviewing it: the same assumptions and the same blind spots on both ends. Code can appear correct, pass its own review, and still be missing requirements entirely.

Notice what it doesn't raise. A diff review can only see what's there, never what was never written, so work that was skipped is invisible to it. Ask a differently-framed question and the gap reappears immediately. The quality of an AI review is bounded by the question a human thought to ask.

5. Make the Risk Call¶

Would this ship at your organization? Judge by blast radius (how much it can break) and use-case sensitivity (how much it matters if it does). Decide the review level it warrants.

Then get peer review, which is non-negotiable when ownership is shared. Swap with the person next to you and review each other's diff. It's the only point today where a human reviews AI-generated code they didn't commission, which is exactly what breaks the loop.

Tip

AI fits into your existing review and governance process; it doesn't replace it. End this module with code you'd put your name on.
