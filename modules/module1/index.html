Module 1: Requirements Gathering and Spec Creation¶

The Codebase¶

Finch Financial is an internal operations console for a fictional neobank. The app is already running with the following functionality built:

  • Sign in via email and password (all users share the password Password123!)
  • Browse and filter customer accounts by status and name
  • Search and filter transactions across all accounts
  • View an account's detail page with transactions, memos, and audit log
  • RBAC: analysts see active and frozen accounts; supervisors can also see closed accounts. Only supervisors can add memos.

Your Task¶

Pick one of the two product requests:

1. Freeze and unfreeze customer accounts when suspicious activity is detected.

An ops analyst notices Northgate Properties just sent a $280,000 wire to Cayman Holdings Ltd, with no prior history of transfers anywhere near that size. They can't freeze the account themselves (that requires a supervisor), so they flag it to their supervisor, who logs in and freezes the account with a reason.

2. Flag suspicious transactions for follow-up review, with a supervisor resolution workflow.

An analyst notices Tran Consulting Group has a series of rapid international wires in both directions. They flag a transaction with a reason. The flag appears in a queue. A supervisor reviews it and resolves it.

See product-requests.md for further details.

This module takes a product request to a spec in one session. You own every decision in it; the agent explores, drafts, and asks. It runs in two halves: understand the ground your feature lands on, then decide and write.

Stay in Ask mode while you explore (the agent can read the repo but not change it). Switch to Plan mode when it's time to write (it can edit files but not execute anything).

Part A: Understand¶

1. Map the Territory with Subagents¶

Exploring a codebase is wide and noisy. Don't do it in your main conversation. Hand each question to a subagent: it reads in its own context window and returns only a summary, so the reading never piles up in yours. Ask for the files, in order, and nothing else.

"I'm adding [your request] and I'm new to this codebase. Use subagents to find: the most similar existing feature, traced from API call to database and tests; the rules the code enforces when the relevant data changes; and the parts of the app this feature would touch. Summaries only. Don't plan or write code yet."

Keep it scoped. Map only the slice your feature actually touches, and avoid ingesting the whole repo.

2. Define Your Validation Criteria (Most Important)¶

Requirements aren't only about behavior; they're about how you'll prove the behavior is right. Ask what the repo already gives you to verify against (the type system, the test setup, RBAC rules, audit-log guarantees). Then turn each expected outcome from the product request into a criterion with a pass condition, one per outcome.

"What does this repo already give me to verify a change against? Then turn the expected outcomes into validation criteria, one per outcome, each with a pass condition."

This is what Module 3 verifies against, so "it should work" won't cut it.

3. Surface the Open Questions¶

Ask what the code can't settle: business rules, edge cases, desired behavior. Those are your decisions, not the agent's. Capture them as questions. You'll settle them in Part B.

"What open questions require my input that you can't settle from the code alone?"

4. Spot-check the Agent¶

Don't take the agent's word for it. Open one or two files it cited and confirm its claims yourself. Note where the agent was right, vague, or wrong.

Part B: Decide and Write¶

Switch to Plan mode.

5. Write requirements.md¶

Have the agent write the requirements from the conversation: the task, the validation criteria, the relevant files, and the open questions. Requirements only: no plan, no code. If it starts planning, stop it.

6. Settle the Open Questions¶

Have the agent interview you: one question at a time, with a proposed default for each. The repo ships an interview skill that does exactly this and records every decision in the file.

"Interview me about the open questions in @requirements.md."

Accept or override each default. When it shows the assumptions it's making, confirm them or correct them. Being on the answering end is what surfaces assumptions you didn't know you were making. This is where ownership is won or lost: rubber-stamp the defaults and you've handed the agent your design.

7. Draft spec.md¶

Now ask for the plan. Phases in dependency order; each phase names the criteria it satisfies and how to check them; every validation criterion traces to a phase. Reject non-steps like "implement X": each phase should say what changes, where, and how you'll know it worked on its own.

"Using @requirements.md, draft a spec.md: phases in dependency order, each naming the criteria it satisfies and how to check them. Every criterion must trace to a phase. No vague steps."

Tip

Stop at a minimum viable spec: one where you understand and accept the architectural decisions and their level of detail. Don't over-invest chasing perfect.

8. Audit it (optional)¶

If time allows, have a fresh subagent check the spec against the requirements: every criterion in a phase, no vague steps, nothing the requirements didn't ask for. A reviewer that didn't write the draft catches what the drafter can't.

Tip

requirements.md and spec.md are the only things that cross into Module 2. The conversation doesn't. If the spec is clear enough that someone else could implement from it, you're ready.

Security note

Don't paste secrets into prompts or have the agent open .env.
